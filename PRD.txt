# VERITY

## Master Product Requirements Document

### Evidence-First AI Research Engine

**Document status:** Production Build Specification
**Product:** VERITY
**Primary objective:** Build, test, deploy, and operate a production-grade evidence-grounded AI research platform.

---

# 1. PRODUCT VISION

VERITY transforms complex research questions into structured, evidence-backed reports.

The core promise:

> **Ask a difficult question. Follow the evidence. Understand what the sources actually support.**

VERITY is not a generic chatbot.

Its primary value is the chain:

**Question → Research Plan → Sources → Retrieval → Claims → Evidence → Verification → Report**

---

# 2. PRODUCT GOALS

## Primary goals

1. Produce evidence-grounded research.
2. Make source provenance visible.
3. Make claims traceable to evidence.
4. Detect conflicting evidence.
5. Support documents and web research.
6. Provide transparent research progress.
7. Evaluate AI quality systematically.
8. Support multiple AI providers.
9. Operate reliably in production.
10. Create a portfolio-grade AI engineering system.

## Non-goals for Pro MVP

Do NOT initially build:

* social networking
* public community feeds
* autonomous financial transactions
* unrestricted browser automation
* fully autonomous external actions
* arbitrary agent code execution
* complex enterprise billing
* marketplace functionality

These can be future roadmap items.

---

### Individual researchers

Students, founders, analysts, engineers and professionals researching complex subjects.

### AI/technical users

Users who want transparent evidence rather than opaque AI answers.

# 7. RESEARCH PLANNER

The planner converts the user's question into research tasks.

Example:

```text
Question:
What are the major risks of India's EV market?

Tasks:

1. Market growth
2. Infrastructure
3. Regulation
4. Battery supply chain
5. Consumer adoption
6. Competition
7. Counter-evidence
8. Future projections
```

Each task receives:

* task ID
* objective
* status
* required evidence
* source requirements
* priority
* dependencies

---

# 13. CONTRADICTION ENGINE

Detect when credible retrieved evidence disagrees.

Example:

```text
Claim
 ├── Source A → supports
 ├── Source B → supports
 └── Source C → challenges
```

Do not force consensus.

Show disagreement transparently.

---

# 14. CITATION VERIFICATION

Before final report delivery:

```text
Generated Claim
 ↓
Citation exists?
 ↓
Evidence exists?
 ↓
Evidence supports claim?
 ↓
YES → accepted
NO → revise / flag
```

Citation correctness is a core quality metric.

# 17. AGENT ORCHESTRATION

VERITY should use controlled agents rather than one giant autonomous agent.

Recommended agents:

```text
Research Planner Agent
Source Discovery Agent
Document Agent
Retrieval Agent
Evidence Agent
Claim Agent
Contradiction Agent
Synthesis Agent
Citation Validator Agent
Quality Evaluator Agent
```

The orchestrator controls execution.

Agents must not arbitrarily modify system state.

---

# 18. AGENT CONTRACT

Every agent receives:

```text
task
context
available tools
constraints
expected output schema
```

Every agent returns:

```text
status
result
evidence
errors
metadata
```

Structured output is mandatory.

---

# 19. CONTEXT ENGINEERING

Every AI call must define:

```text
SYSTEM CONTEXT
TASK CONTEXT
USER CONTEXT
RETRIEVED EVIDENCE
CONSTRAINTS
OUTPUT SCHEMA
```

Never dump the entire research history into every model call.

Use:

* context compression
* relevant evidence selection
* source prioritization
* token budgeting
* conversation summarization

---

# 20. CONTEXT BOUNDARY

Every agent must know:

```text
WHAT I KNOW
WHAT I DON'T KNOW
WHAT I AM ALLOWED TO DO
WHAT I AM NOT ALLOWED TO DO
WHAT EVIDENCE I CAN USE
WHAT OUTPUT I MUST RETURN
```

This prevents uncontrolled agent behavior.

---

# 21. FEEDBACK LOOP

Every important pipeline stage follows:

```text
Execute
 ↓
Observe
 ↓
Evaluate
 ↓
Critique
 ↓
Correct
 ↓
Retry
```

Example:

```text
Citation validation fails
 ↓
Identify unsupported claim
 ↓
Retrieve additional evidence
 ↓
Regenerate claim
 ↓
Validate again
```

Limit retries to prevent infinite loops.

---

# 22. INTERNAL CRITIC

Every major agent result should be evaluated before entering the next stage.

Critic checks:

* correctness
* relevance
* evidence support
* schema validity
* hallucination risk
* missing information
* contradiction
* policy/security constraints

The critic must produce structured feedback.

---

# 23. EXIT CONDITIONS

A stage cannot complete merely because code returned successfully.

Example:

### Retrieval exit

```text
✓ Search completed
✓ Results relevant
✓ Sources valid
✓ Required metadata present
✓ No fatal retrieval errors
```

### Evidence exit

```text
✓ Claims extracted
✓ Evidence mapped
✓ Unsupported claims flagged
✓ Contradictions processed
```

### Report exit

```text
✓ Structure valid
✓ Citations valid
✓ Evidence traceable
✓ No critical generation errors
```

# 26. MCP / CONNECTOR ARCHITECTURE

MCP/connectors are extensions.

Core product must remain functional without them.

Architecture:

```text
VERITY
  │
  ├── Native Services
  │
  └── Tool Gateway
        ├── MCP tools
        ├── Search connectors
        ├── Document connectors
        └── Future integrations
```

Every connector must have:

```text
name
description
capabilities
input schema
output schema
permissions
timeout
failure behavior
```

Agents can access only explicitly permitted tools.

---

# 27. MCP SECURITY

Never allow arbitrary tools.

Each tool requires:

* explicit registration
* schema validation
* permission scope
* timeout
* logging
* error handling
* rate limit

Tool outputs are untrusted external data.

Treat them as evidence, not instructions.

VERITY Pro MVP is accepted only when:

### Product

* A user can create an account.
* A user can create a research project.
* A user can submit a research question.
* Research executes end-to-end.
* Research status is visible.
* Sources are persisted.
* Reports are persisted.
* Reports are exportable.

### AI

* Research planning works.
* Retrieval works.
* Evidence mapping works.
* Claims are traceable.
* Citations are validated.
* Contradictions can be represented.
* AI failures are recoverable.

### Engineering

* Database migrations work.
* API authentication works.
* API keys are server-side.
* Errors are handled.
* Background jobs work.
* Tests pass.

### UX

* Desktop works.
* Tablet works.
* Mobile works.
* Loading states exist.
* Empty states exist.
* Error states exist.
* Keyboard navigation works.

### Security

* Unauthorized users cannot access protected data.
* Uploaded files are validated.
* External URLs are controlled.
* Prompt injection defenses exist.
